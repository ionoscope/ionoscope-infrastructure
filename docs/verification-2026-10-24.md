В предшествующем обходе были два реальных HTTP 429 (HE13N и NO369); очередь

с паузами источника. Проверка не устанавливает непрерывную доступность каждого
15-минутного прогноза между циклами; API продолжает отклонять просроченные цели.

- Обычная интеграция через nginx: 54 сценария, 17 из 17 маршрутов.

- Дополнительно 19 HTTP-проверок работающего стека на реальных станциях:

  доступные кешированные прогнозы и неизвестный код станции.

Низкий CS и недоступность источника воспроизведены в изолированном стенде.
В нём заранее создавался валидный кеш, затем станция становилась недопустимой:
оба POST прогноза и GET статуса возвращали 503, старый кеш не выдавался и не
перезаписывался. Просроченная цель давала `expired`, затем прогноз пересчитывался
из текущих данных. При включённой проверке активности недоступность Data API
блокирует также чтение кеша ответом 502.

При повторном реальном обходе дополнительно проверены GA762 (низкий CS) и
HE13N (реальный HTTP 429 от GIRO): ещё восемь HTTP-проверок прошли, metadata
показывает отсутствие активности/готовых данных, оба POST и GET статуса дают
503. Таким образом, эти причины проверены также на реальном источнике.

После применения последней правки журнала выполнена ещё одна реальная проверка
кеша TR169 после естественного истечения цели 14:45: API пересчитал прогноз на
15:00 (`cached=false`), а следующий запрос вернул тот же результат из кеша
(`cached=true`). Просроченный прогноз не был выдан. Последняя проверка состояла
из двух успешных POST без изменения исходных данных или часов системы.

## Исправления

1. Проверочный скрипт охватывает новый `/api/v1/live/status`; добавлен отдельный
   режим проверки активности станций, устаревшего кеша и ошибок источника.
2. Каждая проверка станции использует своё время начала, а не время начала
   всего обхода. Это исключает устаревание окна запроса из-за очереди обхода.
3. Очередь GIRO ждёт HTTP 429 cooldown и повторно проверяет его после ожидания
   обычного слота. Ранее оставшиеся станции могли получать ошибку без запроса,
   а уже ожидающий поток мог пропустить новое ограничение источника. Запрос,
   получивший 429, остаётся ошибкой; немедленного повторного запроса нет.
4. `start.ps1 -RestartDocker -NoBuild` перезапускает Desktop, ждёт готовности
   Engine и явно поднимает Compose. Проверены порядок команд и ожидание Engine.
   Команда также проверена реальным повторным перезапуском: пять компонентов
   поднялись, все три API стали healthy, обновлённый сборщик начал цикл сразу.
5. Параллельная запись журнала коллектора сериализована блокировкой. На реальном
   Windows bind mount до исправления сохранялось 187 из 800 событий, после —
   800 из 800, без дубликатов. В итоговой загрузке до этой правки были все 18
   непустых файлов станций и 18 завершённых событий, но два события начала
   отсутствовали: это привело к отдельной проверке журнала. Файлы наблюдений
   разных станций записываются раздельно. После правки повторены все 70 тестов
   data/worker и пересобраны контейнеры. Правка касается записи журнала;
   полный расчёт прогнозов проверен описанным выше контрольным циклом.

Обе Compose-конфигурации прошли `docker compose config --quiet`.
Машинные отчёты, снимки реальных данных и журналы сохранены локально в
